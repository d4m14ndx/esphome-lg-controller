# LG Protocol Feature Coverage

This table compares [`protocol.md`](protocol.md) with the current ESPHome implementation. "RX" means the controller decodes a valid frame without using that field as a control. Extended fields are reverse-engineered and may not be sent by every indoor unit; implementation here is not a claim of hardware validation on every model.

| Protocol area | Coverage | Current behavior |
| --- | --- | --- |
| Framing and bus scheduling | Implemented | A rolling header/checksum parser discards bad candidates one byte at a time and times out partial frames. UART input is drained continuously. A non-blocking scheduler waits for 500 ms of bus idleness, verifies echoed sends, and retries the same transaction kind after a missing echo. |
| Type 0 status (`0xA8/0xC8/0x28`) | Control + RX | Supports power, cool/heat/dry/fan/auto, standard fan modes, swing, purifier, target/room temperature, Fahrenheit mapping, thermistor selection, sleep timer, and exact-count zone bitfields. Incoming fan codes 5-7 are preserved and available through `fan_mode_code` rather than treated as corrupt frames. Unrelated reservations and ceiling-height bits are preserved when sending. |
| Type 0 telemetry | Optional RX | Optional sensors expose filter warning, energy-saving, external ventilation, humidifier, auxiliary heater, swirl, Fan Auto, robot-clean, cooling-active, and heating-active. Defrost, preheat, outdoor-unit activity, auto-dry activity, and error code remain standard entities. Unit-only telemetry is not cleared by peer controller frames. Central-control fields and non-sleep reservation controls are not exposed. |
| Type 1 capabilities (`0xC9`) | RX/internal | Correct capability masks shape operation, fan, swing, minimum-temperature, and temperature-step traits. Capabilities are persisted. Zone capability bits are treated as a maximum only; they do not guess the installed zone count. Many installer-capability flags remain informational/unsupported. |
| Type 2 settings (`0xAA/0xCA/0x2A`) | Selected control + RX | Supports slow, low, medium, high, and optional power fan curves, up to four vane positions, auto-dry, and unit-reported min/max target limits. A Type 2 frame is sent only for an explicit local change; receiving the startup settings batch does not automatically echo it back. Unit address, auto-change temperature, auxiliary heater, dry-contact, zone-state mode, robot-clean, and explicit limit overrides are not exposed. |
| Type 3 settings (`0xAB/0xCB/0x2B`) | Selected control + RX | Supports overheating control and unit-only pipe-temperature telemetry. Optional RX sensors expose DRED/overcooling modes, oil and half-degree flags, emergency-heater/group/AP/leak states, indoor/outdoor model and capacity codes, static-pressure and thermal-off fan modes, and low-ambient heating. Byte 10 supplies the exact zone count when `zone_count: 0`; a configured YAML count remains authoritative. These installer fields are telemetry only, not writes. |
| Type 3 polling | Implemented, bounded | The normal startup Type 0 request is tried first. Only a master can issue fallback/periodic `0xAB` queries. Startup retries are bounded by `initial_type_b_retries`; periodic polling is controlled by `type_b_refresh_interval` and can be disabled with `0`. Slave controllers remain passive. |
| Type 4 / Type C status (`0xAC/0xCC/0x2C`) | Optional RX + master reply | Optional RX sensors expose filter hours, occupancy, dual-setpoint state, total energy, high/low setpoints, Type 4 room temperature, deadband, Himalaya cooling, mosquito-away, and comfort-cooling states. With `respond_to_type4: true`, a master mirrors a unit `0xCC` as `0xAC` and refreshes byte 9 from the configured room sensor when available. No Type 4 settings are independently invented. |
| Type 5 (`0xAD/0xCD/0x2D`) | Unsupported/diagnostic | The documented examples are incomplete installer writes and the unit behavior is not sufficiently established. The controller does not decode or transmit Type 5 controls; an optional diagnostic text sensor can report the last valid unsupported frame. |
| Type 6 / Type E (`0xAE/0xCE/0x2E`) | Selected optional RX | Unit subtype `0x80` exposes humidity, fan runtime, indoor-unit runtime, and 0.1-degree room temperature. Extended capabilities (`0x00`), installer settings (`0x10`), and possible air-quality data (`0x11`) remain unsupported and diagnostic-only. |
| Type 7 / Type F (`0xAF/0xCF/0x2F`) | Raw optional RX | Bytes 2-4 from a unit frame are published as `type7_power_raw`. The engineering-value conversion and other fields remain insufficiently verified, so no Type 7 controls or interpreted power entity are exposed. |
| Zones | Selected control + RX | `zone1`-`zone8` are optional schema entries. `zone_count: 1..8` sets an exact authoritative count; `0` waits for a valid Type 3 count bounded by known capability maximum. Type 0 zone bits are decoded only after an exact count is known, avoiding their auto-dry/robot-clean aliases on other units. |
| Unknown and high-risk installer fields | Deliberately unsupported | Test-run, release-delay, central-control, auto-addressing, Type 5 controls, and incomplete Type 6 installer fields are preserved or reported diagnostically where appropriate, but are not user controls. |
